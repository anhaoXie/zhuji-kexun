# 06 · 检测算法与数据集

> 检测模型只写成闭环里的一步，不作为创新点主张。本作品真正的主张在系统层：检测、状态、建议接到同一株。

## 1. 检测任务与模型

| 项 | 内容 |
|---|---|
| 任务 | 叶菜病害目标检测（病害框 + 置信度） |
| 模型 | YOLO11n 轻量化检测（320×320 输入） |
| 前期基础 | 团队 EI 论文（AIAHPC 2025，苹果叶病轻量化检测）中的 AICM 光照补偿模块与训练流程 |
| 部署 | 车端 CanMV K230，ONNX → nncase int8 量化 → kmodel |
| 输出 | 病害框、类别、置信度；按株归并后进入六状态判定 |

`code/training/model/` 保留前期论文的算法复现代码（AICM + YOLO11n），作为本作品轻量化方案的**迁移参考**；`code/training/datasets/` 与 `code/training/bokchoy-baseline/` 提供公开数据上的完整训练链路。

## 2. 多角度 + 补拍为什么有效

同一批测试图上的对比：

| 方案 | 按株 Recall | 误报（每棚次） |
|---|---|---|
| 单张顶视 | 0.78 | 5 株 |
| + 多角度（俯视 + 斜视） | 0.82 | — |
| + 低置信度补拍 | **0.85** | **3 株** |

原因不复杂：顶视只能看叶面，斜视补上心叶、下部叶与叶柄基部；补拍则把「拿不准」的帧重新拍清楚，而不是靠模型硬猜。

## 3. 数据集

### 3.1 公开数据（用于训练链路验证）

| 数据集 | 规模 | 类别 | 许可 | 用途 |
|---|---|---|---|---|
| **Bok Choy（上海青）** | 1,965 张（480 组原图 × 4 倍增强） | 2 类：`diseased` / `healthy` | **CC BY 4.0** | 主数据集：训练流程验证与基线 |
| **PlantDoc** | 2,567 张 | 30 类叶病/健康 | **CC BY 4.0** | 通用叶病预训练/骨干验证，不是本作物 |
| 苹果叶病（前期 EI 论文同源） | 3,171 张 | 4 类 | 见原数据集说明 | 算法流程验证，不能当本作品作物数据 |

来源：Kaggle 镜像（Roboflow Universe 导出），详见 [THIRD_PARTY_NOTICES.md](../THIRD_PARTY_NOTICES.md)。

### 3.2 一个必须处理的坑：增强副本跨集泄漏

Bok Choy 的 1,965 张图只来自 **480 张原图**（4× 增强）。Roboflow 原始划分里，**331/480 组（69%）** 的增强副本同时出现在 train 与 test —— 同一片叶子换个亮度/角度就同时进训练和测试，分数会虚高。

本仓库按「**原图基名**」分组后重划 70/15/15，保证同一原图的所有增强只落在一个 split：

| Split | 组数 | 张数 |
|---|---|---|
| train | 336 | 1,402 |
| valid | 72 | 286 |
| test | 72 | 277 |

> 这与作品中「随机划分 → 按日期划分」的论证是同一件事：**公开数据先排除增强泄漏，再谈指标；真正的泛化结论仍要靠自采的跨日期数据。**

### 3.3 公开数据不能替代现场数据

公开数据只能把模型「训起来、跑通部署」，不能直接支撑作品的现场指标：

- 只有病/健两类，**没有具体病害名**，不能直接产出「病害类型」；
- 框的粒度不一致（整株/叶片），**不是病斑级框**；
- 全部是田间/网图，**不是本作品温室的固定机位、俯视/斜视**，存在域差；
- 没有「同一株跨日期」的配对，**支撑不了六状态与找回率**；
- 没有植保员盲判真值，**支撑不了 κ 与一致率**。

因此作品指标以自采的 2 棚 × ≥50 株 × 3 日期测试记录为准（见 [07 指标与评测](07-metrics.md)），公开数据基线单独列示、不混用。

## 4. 训练与复现

```bash
cd code/training/datasets
python download_datasets.py
python prepare_bokchoy.py
python prepare_plantdoc.py

# 基线训练（YOLO11n / 320 px / 8 epochs / CPU）
yolo detect train model=yolo11n.pt data=bok_choy_yolo/data.yaml \
  epochs=8 imgsz=320 batch=8 device=cpu project=runs name=bokchoy_yolo11n_320
```

### 4.1 公开数据基线结果

| 指标 | 验证集结果 |
|---|---|
| Precision | 0.674 |
| Recall | 0.544 |
| mAP@50 | 0.579 |
| mAP@50-95 | 0.328 |

> 320 px + 8 epochs + CPU 的基线，仅用于验证「数据—训练—评估—导出」链路，**不作为作品指标**。正式训练建议 640 px、30—50 epochs、GPU，并做「按原图分组 vs 随机划分」的对照。
> 本仓库不含训练权重文件（`best.pt`），可用上述命令复现；`results.csv` 与曲线在 `code/training/bokchoy-baseline/`。

## 5. K230 部署链路

```
best.pt ──(ultralytics export)──→ best_320.onnx
        ──(nncase 2.11.0 + K230 target + KPU plugin, int8 PTQ, 48 张校准图)──→ best_320.kmodel (2.93 MB)
        ──(CanMV K230 detect_yolo11.py)──→ 摄像头帧 → KPU → YOLO 后处理 → 屏幕画框
```

| 项 | 内容 |
|---|---|
| 板卡 | CanMV K230 YAHBOOM-1G |
| 固件 | CanMV v1.4.3 |
| 传感器 | GC2093 |
| 量化 | int8 PTQ，校准集 48 张（需用实拍图，不能用公开网图） |
| 验证 | 板端屏幕出现检测框并标注类别/置信度；连续 120 帧无异常 |
| 证据 | `code/demo/firmware/k230/board_verify.jpg` |

> 量化后置信度会偏低（示例：`healthy 0.19`），这是公开数据基线 + int8 量化的正常现象；**板端验证的目标是「链路通」，不是精度指标**。精度需用自采温室数据微调后重新评估。

## 6. 数据集管线

| 脚本 | 作用 |

| `download_datasets.py` | 仅用标准库下载公开数据集 |

脚本与统计口径完全可复核；`stats.json` 记录组数、类别框数与泄漏组数。

## 7. 检测之外：本作品的判断链

```
多帧检测（按株归并）
   ↓
置信度阈值（≥0.8 入档 / 0.4—0.8 补拍 / <0.4 人工）
   ↓
六状态（先误报 → 再处置 → 后病程）
   ↓
管理建议（状态 × 严重度 × 生育期）
   ↓
人工确认与改判留痕
```

检测只是第一步；本作品的可验收性来自整条链，而不是单个 mAP 数字。
